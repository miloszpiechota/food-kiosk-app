Jak dziala skladanie zamowienia i platnosc Stripe

Ten opis dotyczy aktualnego kodu aplikacji Food Ordering Kiosk App. Przeplyw zaczyna sie w React, przechodzi przez NestJS, warstwe Prisma i konczy na rekordach w PostgreSQL.

Najkrotszy obraz procesu: koszyk w bazie danych -> snapshot zamowienia -> Stripe Checkout Session -> redirect do Stripe -> powrot do kiosku -> frontend odswieza status -> backend potwierdza platnosc dopiero po zweryfikowanym webhooku Stripe.

1. Frontend: wybor produktow i koszyk

  1. Aplikacja startuje w apps/web/src/app/router.tsx. Router trzyma stan ekranu: welcome, menu, product-details, basket-review, payment-result.
  2. Uzytkownik wybiera tryb dine-in albo take-out. W aktualnym kodzie to jest tylko stan frontendu (orderMode), uzywany w UI. Nie jest wysylany do API podczas tworzenia zamowienia.
  3. Gdy uzytkownik pierwszy raz dodaje produkt, frontend wywoluje ensureBasket(). Jesli nie ma aktywnego basketId, wysyla POST /api/v1/kiosk/baskets przez funkcje createBasket() z basketApi.ts.
  4. Backend zwraca koszyk z id, sessionId, lista pozycji i suma. Frontend zapamietuje basket.id w basketIdRef, a pozycje i podsumowanie w stanie React.
  5. Dodanie produktu idzie przez addBasketItem(), czyli POST /api/v1/kiosk/baskets/:basketId/items. Ilosc zmieniana jest przez PATCH /api/v1/kiosk/baskets/:basketId/items/:basketItemId, a usuniecie przez DELETE /api/v1/kiosk/baskets/:basketId/items/:basketItemId.

2. Backend: tworzenie i aktualizacja koszyka

  1. Endpointy koszyka sa w apps/api/src/kiosk-basket/kiosk-basket.controller.ts, a logika w KioskBasketService.
  2. createBasket() tworzy rekord Basket ze statusem ACTIVE. Jesli request nie ma sessionId, backend generuje go przez randomUUID().
  3. addItem() sprawdza, czy koszyk nadal jest aktywny, oraz laduje produkt menu dostepny dla aktywnej restauracji i menu. Potem MealConfigurationService wylicza konfiguracje produktu: cene jednostkowa, fingerprint i snapshot konfiguracji.
  4. Zapis pozycji koszyka odbywa sie w transakcji Prisma. Jesli w koszyku istnieje juz taka sama pozycja (basketId + menuProductId + configurationFingerprint), backend zwieksza ilosc. Jesli nie, tworzy nowy rekord BasketItem.
  5. Po kazdej zmianie backend sumuje lineTotal wszystkich pozycji i zapisuje wynik w Basket.subtotalAmount. Dzieki temu frontend nie decyduje o cenie koncowej.

3. Prisma i DB: tabele koszyka

  • Basket mapuje sie na tabele baskets.
  • BasketItem mapuje sie na basket_items.
  • Basket.status moze byc m.in. ACTIVE albo CHECKED_OUT.
  • BasketItem przechowuje snapshot nazwy produktu, cene jednostkowa, ilosc, line total i JSON z konfiguracja. To jest wazne, bo pozniejsza zmiana produktu w menu nie powinna zmienic juz zlozonego koszyka.

4. Frontend: klikniecie "Continue to payment"

  1. Na ekranie BasketReviewPage glowna funkcja to handleContinueToPayment().
  2. Funkcja najpierw tworzy snapshot zamowienia: const order = createdOrder ?? await onCreateOrderSnapshot().
  3. onCreateOrderSnapshot() w routerze wywoluje createOrderSnapshot(basketId), czyli POST /api/v1/kiosk/orders z body { basketId }.
  4. Po udanym utworzeniu zamowienia router czysci lokalny basketIdRef. Koszyk nie powinien juz byc dalej edytowany jako aktywny koszyk.
  5. Dopiero po utworzeniu zamowienia frontend wywoluje createCheckoutSession(order.id), czyli POST /api/v1/kiosk/orders/:orderId/checkout-session.
  6. Jesli backend zwroci checkoutUrl, frontend robi window.location.assign(checkoutSession.checkoutUrl). To jest moment, w ktorym uzytkownik opuszcza aplikacje i przechodzi do Stripe Checkout.

5. Backend: tworzenie snapshotu zamowienia

  1. Endpoint POST /api/v1/kiosk/orders jest w apps/api/src/kiosk-order/kiosk-order.controller.ts.
  2. KioskOrderService.createOrder() wymaga basketId, a potem w transakcji szuka koszyka BasketStatus.ACTIVE razem z pozycjami, produktami i menu.
  3. Jesli koszyk nie istnieje albo nie jest aktywny, backend zwraca blad BASKET_NOT_ACTIVE. Jesli jest pusty, zwraca BASKET_EMPTY.
  4. Backend wylicza restaurantId na podstawie pozycji koszyka. Jesli pozycje pochodza z roznych restauracji, zamowienie jest odrzucane.
  5. Backend liczy subtotalAmount jako sume BasketItem.lineTotal.
  6. Tworzony jest rekord Order ze statusem OrderStatus.NEW i paymentStatus = PENDING.
  7. Razem z zamowieniem tworzone sa OrderItem. Kazda pozycja dostaje snapshot nazwy produktu, typu, ceny, ilosci, line total i konfiguracji.
  8. Na koncu tej samej transakcji koszyk jest aktualizowany do BasketStatus.CHECKED_OUT. Od tego momentu nie jest juz aktywnym koszykiem.

6. Prisma i DB: tabele zamowienia

  • Order mapuje sie na orders.
  • OrderItem mapuje sie na order_items.
  • Order.orderNumber ma format podobny do K-YYYYMMDD-XXXXXX, generowany z daty i fragmentu UUID.
  • Order.paymentStatus zaczyna jako PENDING, potem przechodzi na AWAITING_PAYMENT_CONFIRMATION, a po webhooku moze zostac PAID, FAILED albo CANCELLED.

7. Backend: moment rozpoczecia Stripe

  1. Stripe startuje dopiero przy POST /api/v1/kiosk/orders/:orderId/checkout-session. To nie jest moment tworzenia koszyka ani nawet samo klikniecie w UI; faktycznie Stripe jest wywolywany po istnieniu rekordu Order.
  2. PaymentsService.createCheckoutSession() laduje zamowienie razem z pozycjami, platnoscia i restauracja.
  3. Backend waliduje, ze zamowienie ma pozycje, nie jest juz oplacone i ma poprawna kwote w groszach/centach (toMinorUnits()).
  4. Tworzona jest sesja Stripe: stripe.checkout.sessions.create({ mode: 'payment', ... }).
  5. Do Stripe trafia client_reference_id = order.id oraz metadata: orderId i orderNumber. Te dane pomagaja powiazac sesje Stripe z zamowieniem.
  6. success_url i cancel_url prowadza z powrotem na frontend. URL zawiera checkout=success/cancelled i orderId. Dla sukcesu dodawany jest tez session_id={CHECKOUT_SESSION_ID}.
  7. Kwota Stripe jest jedna pozycja line item: Kiosk order {orderNumber} z kwota order.totalAmount * 100.
  8. Po otrzymaniu checkoutSession.url backend zapisuje lub aktualizuje rekord Payment przez payment.upsert().
  9. W tej samej transakcji backend ustawia Payment.status i Order.paymentStatus na AWAITING_PAYMENT_CONFIRMATION.
  10. Backend zwraca frontendowi checkoutUrl. Frontend przekierowuje uzytkownika do Stripe.

8. Prisma i DB: tabela platnosci

  • Payment mapuje sie na payments.
  • Payment.orderId jest unikalne, czyli jedno zamowienie ma maksymalnie jeden rekord platnosci.
  • provider ma wartosc STRIPE.
  • providerSessionId przechowuje ID sesji Stripe Checkout i tez jest unikalne.
  • providerPaymentIntentId przechowuje ID PaymentIntent, jesli Stripe je zwrocil.
  • amount i currency sa zapisane po stronie backendu na podstawie zamowienia.

9. Powrot ze Stripe do frontendu

  1. Po Stripe Checkout uzytkownik wraca na frontend z parametrami URL, np. ?checkout=success&orderId=... albo ?checkout=cancelled&orderId=....
  2. readPaymentReturnState() w router.tsx odczytuje orderId i checkout. Jesli jest orderId, router pokazuje ekran payment-result.
  3. PaymentResultPage od razu odpytuje backend przez GET /api/v1/kiosk/orders/:orderId.
  4. Ekran odswieza status co 2,5 sekundy, dopoki platnosc nie ma statusu terminalnego: PAID, FAILED albo CANCELLED.
  5. Jezeli Stripe przekierowal z sukcesem, ale webhook jeszcze nie dotarl, UI pokazuje stan "Confirming payment". To jest celowe: frontend sam nie potwierdza platnosci.

10. Backend: webhook Stripe, czyli prawdziwe potwierdzenie platnosci

  1. Webhook odbiera POST /api/v1/webhooks/stripe w apps/api/src/payments/payments.controller.ts.
  2. Aplikacja NestJS jest uruchomiona z rawBody: true w main.ts. To jest potrzebne, bo Stripe wymaga oryginalnego body requestu do weryfikacji podpisu.
  3. Controller wymaga naglowka stripe-signature oraz request.rawBody. Bez tego webhook jest odrzucany.
  4. PaymentsService.handleStripeWebhook() wywoluje stripe.webhooks.constructEvent(payload, signature, webhookSecret). Jezeli podpis jest niepoprawny, backend zwraca blad STRIPE_SIGNATURE_INVALID.
  5. resolvePaymentStatus() mapuje zdarzenia Stripe: checkout.session.completed z payment_status='paid' -> PAID, checkout.session.async_payment_succeeded -> PAID, checkout.session.async_payment_failed -> FAILED, checkout.session.expired -> CANCELLED.
  6. applyCheckoutSessionStatus() szuka rekordu Payment po providerSessionId = session.id. Jesli go nie ma, nic nie aktualizuje.
  7. Jesli platnosc byla juz PAID, backend nie pozwala nadpisac jej pozniejszym statusem innym niz PAID.
  8. W transakcji aktualizowane sa dwa miejsca: Payment.status oraz Order.paymentStatus. To jest moment, w ktorym zamowienie staje sie realnie oplacone.

11. Konfiguracja Stripe i bezpieczenstwo w tym kodzie

  • StripeConfigService.getSecretKey() wymaga STRIPE_SECRET_KEY zaczynajacego sie od sk_test_. Kod wymusza Stripe test mode.
  • getWebhookSecret() wymaga STRIPE_WEBHOOK_SECRET zaczynajacego sie od whsec_.
  • FRONTEND_URL okresla, dokad Stripe ma przekierowac uzytkownika po sukcesie albo anulowaniu.
  • CORS w main.ts dopuszcza frontend z FRONTEND_URL albo domyslnie http://localhost:5173.

12. Statusy: jak je czytac

  • Basket.ACTIVE: koszyk mozna jeszcze edytowac.
  • Basket.CHECKED_OUT: z koszyka utworzono zamowienie; koszyk nie jest juz aktywny.
  • Order.NEW: zamowienie zostalo utworzone, ale w tym kodzie nie ma jeszcze workflow kuchni.
  • PaymentStatus.PENDING: zamowienie istnieje, ale sesja Stripe jeszcze nie zostala utworzona.
  • PaymentStatus.AWAITING_PAYMENT_CONFIRMATION: sesja Stripe istnieje, uzytkownik jest lub byl w Checkout, backend czeka na webhook.
  • PaymentStatus.PAID: zweryfikowany webhook potwierdzil platnosc.
  • PaymentStatus.FAILED: Stripe zglosil nieudana platnosc async.
  • PaymentStatus.CANCELLED: sesja Stripe wygasla albo zostala uznana za anulowana.

13. Wazne ograniczenia aktualnej implementacji

  • Tryb dine-in/take-out nie jest obecnie zapisywany w DB przy zamowieniu. Jest tylko w stanie React i UI.
  • Redirect checkout=success nie ustawia platnosci jako oplaconej. To robi dopiero webhook Stripe.
  • W zamowieniu nie widac jeszcze rozbudowanego procesu realizacji kuchennej; Order.status startuje jako NEW.
  • Kwota dla Stripe jest wysylana jako jedna pozycja "Kiosk order ...", a nie jako osobne produkty z koszyka.
